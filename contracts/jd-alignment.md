# JD 关键词对齐与覆盖报告

> 目标：用**JD 的词汇**重构用户已有事实，让 HR/ATS（简历筛选系统）一眼看到匹配。
> 红线不变：**对齐的是"叫法"，不是"事实"**——素材里没有的技能/经历不能补。

## 一、JD 解析：三档关键词

从 JD 提取关键词后分档（agent 自行判断，写进分析）：

| 档位 | 判定 | 简历里的地位 |
|------|------|--------------|
| **必须匹配** | 任职要求第一条、反复出现的技术 | 必须命中：标题/技能/项目 bullet 都要用 |
| **强相关** | 岗位核心能力（如 RAG、微服务） | 优先命中：放在最相关的项目 bullet 里 |
| **可选加分** | "了解/熟悉即可"、加分项 | 有就写，没有不硬凑 |

提取维度：**岗位名称、公司/团队、核心能力、必备技术栈、加分项、业务领域、经验要求、语言要求**。

## 二、对齐手法（只换叫法，不改事实）

1. **同义替换**：素材写"SpringBoot"，JD 写 "Spring Boot"→ 用 JD 写法；素材写"做了检索增强"
   ，JD 写 "RAG"→ 改用 "RAG（检索增强）"
2. **顺序调整**：JD 最看重的 bullet 排到每段第一句（HR 平均只看前几行）
3. **归并映射**：素材的"用向量数据库检索文档"→ JD 说"向量检索/Embedding"→ 命中
   这两个词
4. **标题对齐**：求职意向/岗位名直接用 JD 的标准岗位名（如 "AI 应用开发工程师" 而非
   "想做 AI 的"）

**禁止**：素材没写过的技能写进技能栏；"了解一点 Docker"改成"Docker 容器化部署经验"。

## 三、覆盖报告（交付时输出，用户要才详细展开）

交付 PDF 时**顺带给一句**覆盖情况；用户要详细分析时输出三段：

```
## 命中
- ✅ 必须匹配（5/5）：Python、FastAPI、RAG、LangChain、MySQL
- ✅ 强相关（2/3）：向量检索、提示词工程
## 不足
- ❌ 未命中必须匹配：Kubernetes（素材无相关事实，无法对齐）
- ⚠️ 弱命中：分布式（素材仅"了解"，未写成关键词）
## 建议
- 若确有 K8s 学习/实操（哪怕教程项目），补进 profile 后重新生成
- 把"了解微服务"改为具体事实（"用 Spring Cloud 做过 XX"）再改写
```

**默认不主动输出**（沿用 output-contract 的匹配分析约定）：交付时提一句
"需要 JD 匹配分析（命中/不足/建议）可以告诉我"。

## 四、ATS 友好检查（关键词对齐的隐含收益）

- 关键词写在**正文**（技能栏/项目 bullet），不要塞进图片/表格/页眉页脚
- 技术名词用 JD 里的完整拼写（`Spring Boot` 而非 `SB`），中英不混（RAG 就写 RAG）
- 岗位名、技术栈与 JD 一致 → 过机器筛；事实与排版好 → 过人工筛

## 五、对齐自检清单

- [ ] JD 的"必须匹配"档关键词，每个都在简历里出现过？（没有的列进"不足"，不硬补）
- [ ] 最相关的 JD 关键词，是否出现在第一段项目的第一条 bullet？
- [ ] 用词与 JD 叫法一致（同义替换完成）？
- [ ] 覆盖报告（命中/不足/建议）已准备，交付时按需给出？
